# 关键设计决策

记录"为什么是这样"——每个决策都写了当时的备选与代价。改代码前先读对应的条目，
否则很容易把某个刻意为之的取舍当成疏漏"修掉"。

格式：**背景 → 选项 → 决定 → 后果**。

---

## ADR-001 用 SQLite 做主存储，并限制单进程

**背景**：需要保存 Agent、会话、消息、运行记录，并保证"收到 done 就能查到"。

**选项**

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| SQLite（选中） | 零部署、单文件、事务完整、可 `sqlite3` 直接排查 | 单写者、不适合多进程 |
| PostgreSQL | 天然多进程、并发强 | 需要额外服务与连接管理，违背"独立运行的基础版" |
| JSON 文件 | 最直观 | 无事务、崩溃易损坏、并发写会丢数据 |

**决定**：SQLite + WAL，`run.py` 固定 `workers=1`。

**后果**

- 部署简单到"装依赖、跑起来"；README 里可以教用户用 `sqlite3` 查数据。
- 无法水平扩展；多实例必须各自一份数据库（等于各自一个世界）。
- 迁移是极简的"版本表 + 顺序脚本"（`schema_version` + `MIGRATIONS`），没有回滚；加表加列要手写一条迁移（见 [development.md](development.md#45-新增表或字段)）。

## ADR-002 会话内串行、会话间并行

**背景**：同一会话的两轮如果并发，第二轮可能读到不含第一轮答案的历史，上下文错乱；
但把整个服务串行又会让不相关的会话互相等待。

**选项**

| 方案 | 问题 |
| --- | --- |
| 全局单锁 | 一个慢模型阻塞所有会话 |
| 数据库行锁 | SQLite 没有行级锁；长事务会挡住所有写入 |
| 进程内按会话的 `asyncio.Lock`（选中） | 单进程内有效，跨进程失效 |

**决定**：`WeakValueDictionary[str, asyncio.Lock]`，按 `session_id` 取锁。

**后果**

- 后一轮一定能看到前一轮已提交的答案（这是"上下文正确"的前提）。
- 用弱引用是为了空闲会话的锁能被回收，内存不随会话数增长；持锁期间有强引用，不会被回收。
- 排队时间**不计入** `MODEL_TIMEOUT_SECONDS`——这是文档里明确声明的语义。
- 跨进程无保证，与 ADR-001 的单进程约束互相支撑。

## ADR-003 用 `request_id` 落库实现"可安全重试"

**背景**：网络超时后客户端不知道"模型到底有没有被调用"，盲目重发可能产生两条回答。

**选项**

| 方案 | 问题 |
| --- | --- |
| 不做去重 | 重试即重复生成，历史里出现两轮一样的问题 |
| 只在内存里去重 | 重启即失效，与"可重试"的承诺不符 |
| 落库 + 唯一约束（选中） | 需要一条运行记录，且要定义哪些状态可重放 |

**决定**：`runs` 表加 `UNIQUE(session_id, request_id)`；只有 `completed` 且内容相同的请求直接重放答案。

**后果**

- 重试语义明确：查 `GET /sessions/{id}/requests/{request_id}` 就能知道有没有落地。
- 相同编号 + 不同内容 → `409 request_conflict`（防止编号被误用成"覆盖写"）。
- **不承诺 exactly-once**：`start_run` 之前崩溃不会留下记录，之后的重复请求仍会再次生成。文档里写清了这一点。

## ADR-004 浏览器 WebSocket 用"一次性票据"

**背景**：浏览器原生 `WebSocket` 不能设置 `Authorization` 头。

**选项**

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 把 token 放 URL（`?token=`） | 最简单 | 长期有效凭证进日志/历史，泄露后果重 |
| Cookie | 浏览器自动携带 | 需要 CSRF 防护；WS 与 HTTP 的 cookie 作用域要额外管理 |
| `Sec-WebSocket-Protocol` 传 token | 不进 URL | 子协议必须是合法 token 字符集，容易出错；调试不直观 |
| 一次性票据（选中） | 短期、单次、可绑定资源；实现只有六十行 | 多一次 HTTP 往返；票据仍会进 URL |

**决定**：`POST /sessions/{id}/ticket` 换票（需 Bearer），`?ticket=` 核销，30 秒、单次、绑定**资源串**。
资源串有两种：`session:<会话编号>`（聊天页）与 `ws:<路径>`（被代理的 WebSocket，由 `/proxy-ticket` 签发）。

**后果**

- token 不再出现在 WS URL 里；即使票据泄露，窗口只有 30 秒且只能用一次。
- 票据**确实**会进 uvicorn 访问日志，这是已知暴露面；README 与 architecture 都写明了，长期留存日志的环境应加 TLS 并收紧日志。
- 票据在进程内存里，与 ADR-001 的单进程约束一致。
- 资源串让同一套机制同时服务"会话流"和"代理前缀"，不需要为浏览器再引入 cookie/CSRF。

## ADR-005 token 用保守字符启发式估算

**背景**：裁剪需要知道"这段文本占多少 token"，但不能假设上游用的是哪个分词器。

**选项**

| 方案 | 精确度 | 代价 |
| --- | --- | --- |
| `tiktoken` | 对 OpenAI 模型接近精确 | 多一个依赖，首次需下载词表，且兼容服务未必同一分词器 |
| 只按字符数 | 差 | 中英文差异巨大（1 字 vs 4 字符） |
| 宽字符 1/字 + 其他 3 字符/token（选中） | 中文准，英文偏保守 | 依赖全局常量，不随模型变化 |
| 用上一轮 `usage.prompt_tokens` 校准 | 事后更准 | 首轮没有样本；实现更绕 |

**决定**：`estimate_tokens()` 纯函数，宽字符 1 token/字，其余 3 字符/token 向上取整，每条消息 +4。

**后果**

- 零依赖、可复现、单测能直接断言。
- 估**低**会重新触发上游 400（回到最初的问题），估**高**只是少带一点历史，代价不对等——所以故意偏保守。
- 云端大窗口 + 纯英文场景会少用一部分预算，属于可接受的浪费。
- 未来若要精确，可换 `tiktoken` 或用 `usage` 回填系数，`build_context` 的接口不需要改。

## ADR-006 超预算的处理：整对丢弃 + 省略提示 + 413

**背景**：历史无限增长，模型窗口有限。截断方式直接影响用户对"模型为什么失忆"的理解。

**选项**

| 方案 | 问题 |
| --- | --- |
| 按条数保留最近 N 条 | 与实际 token 无关，长消息仍会超限 |
| 截断当前提问 | 用户不知道自己的话被删，答案会答非所问 |
| 调模型做摘要 | 多一次调用（费用/延迟/失败路径），基础版不值得 |
| 整对丢弃 + 提示 + 413（选中） | 早期内容确实丢了，但用户能看到提示 |

**决定**：从最旧的一问一答开始丢；丢过就插一条 system 提示"（较早的 N 条对话已省略…）"；
连"system + 当前提问"都放不下则 `413 context_too_large`，且**不写运行记录**。

**后果**

- 历史严格保持"用户开头、成对出现"，不会造出上游拒绝的形状。
- 413 不写记录，带来一个好性质：改短输入后可以用**同一个** `request_id` 重试。
- 数据库里的历史一条不删；`GET /messages` 始终是全集。
- 用户会看到"已省略早期 N 条消息"的提示（浏览器页），避免误以为模型坏了。

## ADR-007 模型请求默认不使用系统代理

**背景**（一次真实事故）：Windows 上开着代理软件时，httpx 默认读取系统代理，
把发往 `127.0.0.1` 的本地模型请求也送去代理，结果所有模型调用都变成 `502 model_http_error`。
本项目的 8 个测试里曾有 7 个因此失败。

**选项**

| 方案 | 问题 |
| --- | --- |
| 沿用 httpx 默认（`trust_env=True`） | 本机模型服务被代理拦截，且报错完全看不出原因 |
| 硬编码 `trust_env=False` | 需要代理访问远程服务的人没法用 |
| 增加开关，默认 `False`（选中） | 多一个配置项 |

**决定**：`MODEL_USE_SYSTEM_PROXY`，默认 `false`；显式设为 `true` 才读取 `HTTP(S)_PROXY`。

**后果**

- 本机/内网模型开箱可用；需要代理时改一行配置。
- 代价是多一个配置项和一段文档；换来的是"不会莫名其妙 502"，值得。
- 回归测试：把 `HTTP_PROXY` 指向不可用端口，断言仍能正常调用（`test_model_client_ignores_system_proxy_by_default`）。

## ADR-008 不引入 ORM、依赖注入框架与仓储抽象

**背景**：项目定位是"易于理解"，读者要能在半小时内读懂整条链路。

**决定**：SQL 直接写在 `storage.py`；依赖通过构造函数手工传入；`create_app(settings)` 一个工厂函数搞定。

**后果**

- 全项目约 1,150 行 Python（含注释，不含测试），没有隐式行为，栈追踪短。
- 没有自动迁移、没有懒加载、没有连接池魔法——也没有它们带来的问题。
- 表结构变更要手写 SQL；测试要自己造 `Settings`。这是刻意的取舍。

## ADR-009 错误统一为 `GatewayError`，但呈现分两层

**背景**：HTTP 与 WebSocket 需要不同的错误载体，但业务层不应该知道 HTTP 状态码之外的东西。

**决定**：业务层只抛 `GatewayError(status_code, code, message)`；`error` 对象只含 `code` + `message`，
其余信息放外层。两种载体各只有**一种**形状：

- HTTP：`{"error": {...}}` + 可选顶层 `session_id` / `request_id` / `run_id`；
- WebSocket：`{"type": "error", "status": int, ...}` + 同一套 `error` 对象。

**后果**

- 业务代码不为"HTTP 还是 WS"分叉；客户端只需一条规则：错误码看 `error.code`。
- 生成位置不同（路由层异常 vs 生成器内事件），但都由 `app.py` 收敛成各自的唯一形状。
- 代价：HTTP 体里没有 `status` 字段（由状态行表达），WS 体里有——载体差异保留，这是有意的。
- 早期版本存在两种 HTTP 错误体与四种 WS 错误形状，已统一（`status_code` 字段改名为 `status` 并下放到外层）。

## ADR-010 浏览器页用单文件、无构建步骤

**背景**：需要一个能真正对话的页面，但不想引入 node/打包/前端框架。

**决定**：`web/chat.html` 一个文件，内联 CSS/JS，由 `GET /` 直接返回。

**后果**

- 不需要 `npm install`，改一行刷新即生效；离线可用（无 CDN）。
- 所有输出用 `textContent` 写入，天然免疫 HTML 注入。
- 没有组件化与类型检查，页面逻辑复杂到一定程度就该拆分了。
- token 存在 `localStorage`，同机其他用户可见；共享机器上应改为"每次输入、不落盘"。

## ADR-011 反向代理：配置化前缀、HTTP + WebSocket、多上游轮询

**背景**：希望"通过网关访问其他项目"，让多个本地服务共用一个入口和一套 token。

**选项**

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| 进程内挂载别的 ASGI 应用 | 一行代码、零网络开销 | 必须同语言同进程、可导入；依赖冲突无解 |
| 反向代理（选中） | 任意语言、任意进程、独立部署 | 需要处理流式、头、超时、WS 双向桥接 |
| 交给 Caddy/Nginx | 生产级特性齐全、不写代码 | 多一层进程；网关自己不知道这些路由 |

**决定**：`routes.json` 配置"前缀 → 一个或多个上游"，网关为每个前缀注册 HTTP 与 WebSocket 两类路由；
选路用平滑加权轮询，连接失败的上游进入冷却；HTTP 流式回写，WS 用两条协程桥接；
浏览器可通过 `/proxy-ticket` 换票连代理的 WS。

**后果**

- 一个入口 + 一套 `GATEWAY_TOKEN` 覆盖所有被代理的服务；上游不需要各自暴露鉴权。
- 网关自己的 token 与 `?ticket=` 都不转发给上游，需要时用路由里的 `headers` 显式注入上游凭据。
- 目标只来自配置，客户端无法指定 URL，所以不会变成 SSRF 跳板。
- 最长前缀优先：`/a/b/` 不会被先声明的 `/a/` 遮蔽（排序在加载时完成）。
- 边界：不做主动健康检查（靠被动冷却）、不做粘性/服务发现、不改请求体、不代理非 HTTP 协议。
- 选路状态（权重计数、冷却截止时间）在进程内存里，与 ADR-001 的单进程约束一致。
- 回环用 `X-Gateway-Proxy: 1` 识别，比比较 host/port 更可靠（尤其在反向代理后面）。

## ADR-012 代理的失败切换只发生在"连接阶段 + 幂等方法"

**背景**：多上游时，某个上游挂了应该自动换下一个；但重放请求可能产生重复副作用。

**选项**

| 方案 | 问题 |
| --- | --- |
| 任何失败都重试 | POST 可能被上游执行两次，出现重复订单/重复写入 |
| 读超时也重试 | 上游可能已经处理完、只是回得慢，重试等于重复执行 |
| 只在连接阶段 + 幂等方法重试（选中） | 语义安全，但"上游处理到一半挂掉"时仍然只能报错 |

**决定**：只有 `httpx.ConnectError` / `ConnectTimeout`（请求没被处理）且方法属于 GET/HEAD/OPTIONS 时，
才换下一个上游；读超时返回 504、不重试也不冷却；响应一旦开始回写绝不重试。

**后果**

- POST 在最坏情况下会直接 502，而不是"可能成功也可能重复"——这是刻意的，把不确定性留给调用方决定。
- WS 在 `accept` 之前可以换上游，`accept` 之后无法迁移（协议没有重放），只能关闭。
- 读超时不算"上游坏了"，所以不触发冷却；否则一个慢接口会被误判成宕机。
- 测试锁定了三点：GET 失败切换、POST 不重放、读超时返回 504。

## ADR-013 主动探活：GET 默认、4xx 算活、全挂仍兜底

**背景**：被动冷却只能发现连接失败；"能连上但一直 500"的上游会被轮询一直选中。

**选项**

| 方案 | 问题 |
| --- | --- |
| 纯失败率熔断 | 需要滑动窗口；恢复慢；慢失败发现不及时 |
| 主动探活 + 冷却（选中） | 需要上游提供轻量端点；探活会进上游日志 |
| 交给外部负载均衡 | 网关失去视角，多一层组件 |

**决定**：独立模块 `proxy_health.py` 起一个后台协程，按最小间隔探测所有开启探活的上游；
默认 `GET /health`；**4xx、405、501 视为存活**，只有 5xx 与连接失败计入失败；
连续 `failures_to_down` 次失败标记 `healthy=False`，连续 `successes_to_up` 次成功放回。

**后果**

- 默认是 `GET` 而不是 `HEAD`：最初用 HEAD，结果一个只实现 GET 的正常上游回 501 被判死（真实踩坑）。
- 4xx 不判死，是为了让"探活路径需要鉴权/写错路径"这类配置问题不至于灾难性摘除。
- 选路顺序变成"健康且未冷却 → 不健康但未冷却 → 冷却中"；**全部不健康时仍会真实尝试**，
  否则健康检查本身成了单点故障。
- 状态通过只读接口 `GET /proxy-status` 暴露，便于确认"到底谁被摘了、为什么"。
- 已知简化：一个后台任务用最小间隔，不支持每条路由独立周期；没有滑动窗口。

## ADR-014 日志：JSON Lines + 队列写盘 + 产出端脱敏

**背景**：原代码只有零散 `logging` 调用，`run.py` 从未配置 → INFO 全部丢失；
uvicorn 访问日志无法脱敏，会把 `?ticket=` 原样写进日志；排查问题缺少 trace id 与请求参数。

**选项**

| 方案 | 问题 |
| --- | --- |
| stdlib logging + 自写 JSON Formatter（选中） | 需要自己写 formatter/context/轮转，但零新依赖、与 uvicorn 兼容 |
| structlog | 结构化上下文更顺手，但多一层抽象且要和 stdlib 桥接 |
| loguru | 开箱即用，但与 stdlib/uvicorn 生态割裂 |

**决定**：stdlib + `JsonFormatter` + `QueueHandler/QueueListener`；按 logger 名路由到
`access/app/proxy/auth/audit/services/<name>` 目录；访问日志用纯 ASGI 中间件旁路采集；
脱敏在写入前完成；uvicorn 自带 access 日志关闭。

**后果**

- 日志是标准 JSON Lines，可直接被 Vector/Filebeat 采集，不绑定具体"日志框架服务"。
- 请求体只旁路复制前 `PARAM_MAX_BYTES` 字节，且不重建 Request，所以不影响业务解析。
- 正文默认只留 200 字预览（可配置为 0），在"可排查"与"不泄露对话"之间取平衡。
- **trace_id 必须在产出线程抓取**：格式化在队列线程执行，contextvars 不会跟过去，因此用 `TraceIdFilter` 把它写进记录。
- 队列意味着进程崩溃时可能丢最后几条日志；审计留痕需要额外的强保证（见阶段 2）。
- 日志字段从此是事实上的对外契约，字段变更要同步 README 与 architecture。

## ADR-015 审计：DB + 文件双写，且"旁路失败不阻断业务"

**背景**：多人使用后需要回答"谁在什么时候删了会话/Agent、谁登录失败"；日志文件适合采集但不适合按条件查询。

**选项**

| 方案 | 问题 |
| --- | --- |
| 只写日志文件 | 查询要外部系统；文件轮转删除后难以追溯 |
| 只写数据库 | 无法被日志采集；库被改后没有旁证 |
| DB + 文件双写（选中） | 需要保证两边一致与失败处理 |

**决定**：`audit_log` 表存结构化事件（可查询），同时用 `gateway.audit` logger 写 `audit/` 文件（可采集），
同一条事件共享 `id` 与 `trace_id`。审计写入用 try/except 包裹：失败只记 ERROR，不改变业务响应。

**后果**

- `GET /audit` 支持按 `action/result` 过滤与分页；阶段 3 会限定为管理员。
- **fail-open 是刻意的**：内部工具里"审计库暂时不可用就拒绝所有写操作"代价过高；代价是极短窗口内的事件可能只有文件、没有库记录。
- 没有防篡改保证：需要合规时把 `audit` 日志采集到外部 WORM/SIEM，网关不承诺自己也做不到的事。
- 审计只记变更与认证事件，不记对话正文（与日志的脱敏原则一致）。

## ADR-016 本地账号：scrypt + 不透明会话 Cookie + Origin 校验

**背景**：局域网多人使用，需要区分身份与可吊销的登录态；不引入外部 IdP，也不新增依赖。

**选项**

| 方案 | 问题 |
| --- | --- |
| 继续共享 token | 无法区分人、无法单独吊销、审计只有一个 actor |
| 自签 JWT 放浏览器 | 注销困难；浏览器存 token 有 XSS 风险 |
| 服务端会话 + 不透明 Cookie（选中） | 需要查库校验（可缓存）；但可即时吊销、实现透明 |
| 外部 OIDC | 最规范，但需要 IdP 与回调，超出当前范围 |

**决定**：`users` + `auth_sessions`；密码用 stdlib `scrypt`；Cookie 只放随机 token，
库里存 SHA-256；CSRF 依赖 `SameSite=Lax` + `Origin/Sec-Fetch-Site`；登录按 IP+账号限速；
`GATEWAY_TOKEN` 在 local 模式下保留为管理员身份，便于脚本渐进迁移。

**后果**

- 零新增依赖；`python -m gateway.admin create-user --admin` 是唯一引导入口（避免密码进 `.env`）。
- 每个请求要查一次会话（索引查询，约 1–2ms；后续可用 30 秒内存缓存优化，代价是撤销延迟）。
- 会话/密码变更可即时吊销；重置密码会踢掉该用户全部会话。
- CSRF 只对 Cookie 认证生效；Bearer 请求不受影响，脚本无需改动。
- 没有多因素、没有自助注册、没有密码找回——局域网内部工具，由管理员维护账号。
- 登录限速在进程内存，重启清零；这是可接受的简化。
